## 1. 甄别方法

1. 对每条指控定位到具体文件与行为，必要时做数学复算（首日任务量）与运行时验证（日期星期）。
2. 区分三个时间层次：**历史缺陷（曾存在）、当前状态（已修复/仍存在）、PRD 承诺层级（Must/Should/Could）**。用户报告把三者混在一起，是其评分与代码事实偏差的主要来源。
3. "PRD 写了但没做"不等于虚假宣传：先核对 MoSCoW 层级与产品内是否存在入口；只有"用户点得到入口但拿不到东西"才按名实不符处理。

## 3. 高争议点专项核实结论

1. **"转化率小样本伪精确"——与代码事实不符。** 双端证据闭合：`stores/funnel.ts` L118-119 以终态（closed）数量 ≥5 为门槛，`FunnelView.vue` L171-177 在门槛不满足时不渲染任何百分比，改为"积累中"提示。该指控若针对历史版本可能成立，对当前代码不成立。
2. **"XSS/注入/越权"——与代码事实不符。** 参数化：服务端所有 SQL 为 `prepare` + `?` 绑定（见 `auth.routes.ts` L43/L52/L71/L91、`sync.routes.ts` L40/L58/L69/L87）；自动转义：前端全部用户内容走 Vue 插值；v-html：全工程仅 `Icon.vue` L101 一处，数据源为编译期静态字典 `ICON_PATHS`，按 name 查表且有 fallback，不接收用户输入；越权：JWT 载荷仅 `sub`（`token.ts` L10-13），`sync.routes.ts` 全部语句以 `WHERE user_id = ?` + `req.userId` 隔离，渗透报告有 alice/bob 交叉实测。另无 `eval`/`document.write`。
3. **"静默吞错"——客观缺陷，历史主干已修、残留仍在。** 已修：`main.ts` L24 显式 `setActivePinia`，守卫加 `ready` 门禁，`CountdownHero` L66-69 补空状态。残留：两处空 catch 块与一处静默降级，本次收口。
4. **"桌面底部 Tab 重复"——已修复。** `TabBar.vue` L45 默认 `display: none`，L54-58 仅在 `@media (max-width: 767px)` 显示；桌面导航由 `AppSidebar.vue` 承担，不存在双导航并存。
5. **"后端非法 JSON 返回 500"——已修复为 400。** `middleware/error.ts` L29-38 识别 body-parser 错误的 `status` 字段：非法 JSON=400、过大=413、编码错误=415；生产环境 4xx 返回通用文案。渗透报告 L41-44 有修复与复测记录。
6. **"首日 240 分钟、未采集每日产能"——客观缺陷，完全属实。** 引导仅问每周作战天数（`OnboardingView.vue` L148-151），planner 无每日产能字段与约束（`planner.ts` L48-59、L434-468）；默认参数下 M0 三个任务（60/120/60 分钟）全部落在首日，合计恰好 240 分钟，且三者均被标为 MIT。这是本次必须修复的真实问题。

## 8. 结论：成熟度判断与上线条件

1. 用户报告的 5.5/10 建立在"历史缺陷 + 当前缺陷 + Should 延期 + 个人风格偏好"混合计分之上，存在系统性低估：

   - 真实成立的核心问题集中于三点：**缺每日产能输入导致首日 240 分钟（核心算法工程化不足）、漏斗交互名实不符、备份恢复无闭环**；另有 PWA 未实际落地、云同步前端零接入两个 PRD 名实差距。
